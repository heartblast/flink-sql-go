# flink-sql-go v0.1.2 릴리스 노트

- 릴리스 버전: `v0.1.2`
- 지원 Apache Flink 버전: `1.20.4`
- 지원 SQL Gateway REST API: `v1`, `v2`, `v3`
- 기준 Go 버전: `1.26.5`
- 릴리스 예정일: 2026-07-24

## 개요

`v0.1.2`는 `v0.1.1`의 공개 module 경로와 기능 API를 유지하면서 session, heartbeat,
operation cleanup과 streaming 수명주기의 운영 안정성을 강화한 릴리스다.

장시간 실행에서 발생할 수 있는 heartbeat 중단, 공개 DTO를 통한 내부 상태 변경,
Close와 실행 중 operation의 경쟁, Observer block, closed-session 기록 증가와 반환 객체 변조를
방지한다. 비멱등 SQL 제출의 오류 분류와 Changelog Materializer 복구 기능도 보강했다.

## 설치

```text
go get github.com/heartblast/flink-sql-go@v0.1.2
```

```go
import (
```

## 주요 변경사항

### Session과 heartbeat 안정성

- 개별 heartbeat 요청 timeout이 발생해도 runner가 종료되지 않고 다음 주기에 다시 시도한다.
- 연속 실패가 임계값에 도달하면 `DEGRADED`, 이후 성공하면 `HEALTHY`로 복구한다.
- 공개 `Session`을 client 내부 session record와 분리했다. 반환된 `Handle`, `Name`과
  `Properties`를 변경해도 내부 route와 `StatementValidator` 문맥은 바뀌지 않는다.
- 성공적으로 닫힌 session 기록은 최근 1,024개까지만 보관한다.
- server가 동일한 session handle을 다시 발급해도 이전 Close cache가 새 session 상태를
  제거하지 않게 했다.

### Close와 operation cleanup

- `GatewayClient`, `ManagedSession`과 `SerializedSession`이 실행 중인 수집형 실행과 stream을
  추적한다.
- Close는 신규 실행 차단, 실행 context 취소, operation cancel/close 완료 대기,
  heartbeat 종료와 server session 종료 순서를 따른다.
- wrapper Close의 context가 stream cleanup까지 전파되어 호출자의 종료 deadline을 지킨다.
- 첫 session Close가 context 오류로 끝나도 다음 Close에서 server-side cleanup을 다시 시도한다.
- operation cancel에 전체 cleanup 시간의 최대 절반만 사용하여 cancel timeout 이후에도
  CloseOperation을 시도한다.
- cancel과 close 오류는 원래 실행 오류를 덮어쓰지 않고 `ExecutionError`에 함께 보존한다.

### 비멱등 SQL 오류 분류

- SQL 제출 POST는 자동 재시도하지 않으며 `APIError.Retryable`도 `false`로 반환한다.
- SQL 제출 중 HTTP 408, 429와 5xx 응답은 operation 생성 여부를 확정할 수 없는 경우
  `ExecutionOutcomeUnknownError`로 분류한다.
- 확정적인 4xx SQL 거부와 요청 전송 전 오류는 결과 불명확 오류로 오분류하지 않는다.
- 완전한 non-2xx 응답 수신을 나타내는 `ResponseReceived` request phase를 추가했다.

### Stream과 Observer 격리

- `StreamResults` producer를 client 실행 추적에 포함하여 consumer가 읽기를 중단해도
  context 취소 또는 `GatewayClient.Close` 후 종료된다.
- Observer callback의 실행 시간과 동시 실행 수에 상한을 적용한다.
- 기본 Observer timeout은 100ms, 최대 동시 실행 수는 16이다.
- 동시 실행 상한을 초과한 관측 event는 HTTP 요청과 cleanup 경로를 보호하기 위해 버린다.
- Observer panic은 client 실행과 cleanup에 전파되지 않는다.

### Handle 검증과 오류 문자열

- 모든 공개 session·operation API가 network 호출 전에 handle을 공통 검증한다.
- 빈 값, 공백만 있는 값, 제어문자, 잘못된 UTF-8과 4,096 byte를 초과하는 handle을 거부한다.
- slash와 일반 Unicode를 포함한 유효한 불투명 handle은 URL path segment로 escape한다.
- SQL Gateway와 Job REST client의 server 오류 메시지를 유효한 UTF-8 경계에서 제한한다.
- 잘못된 UTF-8 byte는 대체 문자로 정리하여 log와 JSON encoder에 유효한 문자열만 전달한다.

### Decoder와 반환값 격리

- `RowAccessor`가 column, nested `LogicalType`, pointer metadata와 raw JSON을 깊게 복사한다.
- object형 nested ROW에서 schema에 없는 field를 `json.RawMessage`로 보존한다.
- stream의 operation event, result page, row와 nested raw JSON을 내부 상태와 분리한다.
- caller가 반환된 operation handle이나 row를 변경해도 실제 paging과 cleanup route는 바뀌지 않는다.

### Changelog Materializer

- `ApplyUpdate(before, after)`로 `UPDATE_BEFORE`와 `UPDATE_AFTER`를 원자적으로 적용할 수 있다.
- `RollbackPending()`으로 중단된 update pair를 폐기하고 이전 snapshot을 유지할 수 있다.
- `PendingUpdates()`로 불완전한 update 수를 확인할 수 있다.
- primary key JSON의 공백, object key 순서와 문자열 escape 표현을 정규화한다.
- 삭제할 때 insertion-order slice를 매번 이동하지 않고 O(1) tombstone index와 조건부
  compaction을 사용한다.

## 공개 API 추가

```go
type Config struct {
    ObserverTimeout     time.Duration
    ObserverMaxInFlight int
}

const ResponseReceived RequestPhase = "RESPONSE_RECEIVED"

func (m *Materializer) ApplyUpdate(before, after flinksqlgateway.Row) error
func (m *Materializer) RollbackPending() int
func (m *Materializer) PendingUpdates() int
```

기존 공개 type, field와 method는 제거하지 않았으며 source compatibility를 유지한다.

## 업그레이드 시 확인사항

- SQL 제출 408, 429와 5xx 오류를 `Retryable`만 보고 자동 재제출하던 코드는
  `ErrExecutionOutcomeUnknown`을 확인하고 operation 또는 Job 생성 여부를 먼저 조회해야 한다.
- Observer가 100ms보다 오래 걸릴 수 있으면 `ObserverTimeout`과 `ObserverMaxInFlight`를
  운영 환경에 맞게 설정해야 한다.
- 기존에 빈 값이나 제어문자가 포함된 handle을 전달하던 코드는 network 호출 전에 오류를 받는다.
- 불완전한 changelog update가 발생할 수 있는 consumer는 resync 시 `RollbackPending()`을
  호출하거나 `ApplyUpdate()`를 사용해야 한다.

## 알려진 제한

- 실제 Flink 1.20.4 환경의 장시간 streaming, session expiry와 API version별 contract matrix는
  별도 integration test가 필요하다.
- Windows race detector는 C compiler `gcc`가 있는 환경에서 별도로 실행해야 한다.
- Observer timeout은 callback goroutine을 강제로 종료하지 않는다. 실행 중인 callback이 반환할
  때까지 slot을 점유하며, 상한에 도달하면 후속 event를 버린다.
- channel 기반 `StreamResults`의 소비를 중단할 때는 context를 취소하거나 client를 닫아야 한다.
  신규 코드는 명시적인 `Close`를 제공하는 `ResultStream` 사용을 권장한다.
- trusted reverse proxy용 NextResultURI rewrite resolver, Linux build script, cross-platform CI,
  SBOM과 provenance 자동 생성은 포함하지 않는다.
- 인증 방식과 사용자 권한 정책은 상위 서비스가 제공해야 한다.
