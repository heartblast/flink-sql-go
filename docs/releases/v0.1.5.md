# flink-sql-go v0.1.5 릴리스 노트

- 릴리스 버전: `v0.1.5`
- 지원 Apache Flink 버전: `1.20.4`
- 지원 SQL Gateway REST API: `v1`, `v2`, `v3`
- Session Setup 지원 REST API: `v2`, `v3`
- 기준 Go 버전: `1.26.5`
- 릴리스 예정일: 2026-07-29

## 개요

`v0.1.5`는 catalog, database, table과 현재 session scope를 network 호출 전에 검증하고
`configure-session`으로 적용하는 선언형 Session Setup API를 추가한다. 기존 `SessionRecipe`는
`/statements` 기반 범용 replay로 유지되며 기존 공개 `Client` interface도 변경하지 않는다.

setup은 catalog → database → table → `USE CATALOG` → `USE database` 순서로 실행된다. CREATE
대상은 library가 완전 수식하고 식별자와 option 문자열을 안전하게 quoting한다. 부분 실패와 결과
불명확 상태를 별도 결과와 typed error로 확인할 수 있으며 자동 재시도나 자동 `DROP` rollback은
수행하지 않는다.

## 설치

```text
go get github.com/heartblast/flink-sql-go@v0.1.5
```

## 신규 공개 API

- `SessionSetupPlan`, `CatalogSetup`, `DatabaseSetup`, `TableSetup`
- `SessionSetupStep`, `SessionSetupStepKind`, `CompileSessionSetup`
- `SessionSetupOptions`, `SessionSetupStepResult`, `SessionSetupResult`
- `SessionSetupExecutor`
- `GatewayClient.ApplySessionSetup`
- `GatewayClient.OpenSessionWithSetup`
- `ErrConfigurationOutcomeUnknown`, `ConfigurationOutcomeUnknownError`
- `ErrSessionSetupVerification`, `SessionSetupError`
- Session Setup lifecycle observation event

`SessionSetupExecutor`는 기존 `Client`와 별도 interface다. v0.1.4 `Client`를 구현한 외부 mock이나
wrapper는 신규 메서드를 추가하지 않아도 계속 compile된다.

## Compile과 실행 흐름

`CompileSessionSetup`은 network를 호출하지 않고 다음을 모두 확인한다.

- 빈 plan, 빈 식별자와 제어문자
- catalog, database와 table 중복 정의
- catalog가 없는 database/current database 조합
- 완전 수식되지 않은 table target
- 완전한 `CREATE TABLE` 문이 전달된 `TableSetup.Statement`
- 빈 catalog option과 잘못된 sensitive key

`TableSetup.Statement`는 library가 생성한 완전 수식 target 뒤의 definition만 받는다. SQL parser나
문자열 기반 객체명 추측은 추가하지 않았다. option key는 정렬하고 작은따옴표를 두 번 써 항상
결정적인 SQL literal을 만든다.

같은 session의 `ConfigureSession`과 Session Setup은 context-aware gate로 직렬화한다. 서로 다른
session은 병렬로 실행할 수 있다. setup POST는 한 번만 전송하고 후속 step은 앞 step 성공 응답을
확인한 뒤 실행한다.

## 결과 불명확 오류

`ConfigureSession`과 setup step은 다음 경우 `ErrConfigurationOutcomeUnknown`으로 분류한다.

- 요청 byte가 전송됐을 가능성이 있지만 response header를 받지 못함
- 성공 response body를 완전히 읽지 못함
- HTTP 408 또는 429
- HTTP 5xx

`RequestNotSent`는 결과 불명확으로 분류하지 않는다. 결과 불명확 DDL을 자동으로 재실행하지 않으며
`ConfigurationOutcomeUnknownError`는 SQL 없이 session, step index, step kind와 request phase만
보고한다.

## Metadata 검증과 실패 cleanup

`VerifyMetadata`는 `ListCatalogs`, `ListDatabases`, `ListTables`, `ListViews`를 재사용한다.
`VerifyTableSchema`는 `DescribeTable`까지 수행한다. DDL 성공과 metadata 검증 성공은 각각
`Applied`, `Verified`에 기록되며 검증 실패가 DDL 미적용을 뜻하지 않는다.

`OpenSessionWithSetup` 실패 시 기본값은 생성한 session을 제한된 background context로 닫는 것이다.
`KeepSessionOnFailure`로 session을 유지할 수 있다. cleanup은 session 종료일 뿐 rollback이 아니며,
성공했거나 결과가 불명확한 CREATE가 있으면 `PersistentChangesMayRemain`을 반환한다.

## 비밀정보 보호

- 기본 민감 key는 `password`, `secret`, `token`, `access-key`, `secret-key`와 대소문자 및 구분자
  변형을 포함한다.
- `CatalogSetup.SensitiveKeys`로 caller key를 추가할 수 있다.
- 구조화할 수 없는 table definition은 `TableSetup.Sensitive`로 전체 server message redaction을
  요청할 수 있다.
- SQL, option map과 secret은 result, typed error, request Observer와 lifecycle event에 저장하지
  않는다.
- Gateway가 SQL, raw secret 또는 작은따옴표 escape 값을 오류에 반사하면 관측 전에
  `********`로 치환한다.

## 업그레이드 시 확인사항

- REST API v1 client의 기존 기능은 유지되지만 Session Setup은 network 호출 전에
  `ErrUnsupportedAPI`를 반환한다.
- 알 수 없는 미래 REST API version은 configure-session 지원을 추측하지 않는다.
- `TableSetup.Statement`에 완전한 `CREATE TABLE` 문을 전달하지 말고 target 뒤의 definition만
  전달해야 한다.
- `default_catalog`는 in-memory이므로 객체 수명이 session에 묶인다. HiveCatalog 같은 영속
  catalog의 객체는 실패 cleanup 뒤에도 남을 수 있다.
- 결과 불명확 오류에서는 같은 DDL을 무조건 재실행하지 말고 read-only metadata와 운영 정책으로
  조정해야 한다.

## 검증 결과

Go 1.26.5와 `httptest.Server` 기반 mock SQL Gateway에서 다음 항목을 검증했다.

- compile 순서, option 정렬과 backtick/작은따옴표 escape
- v1 및 알 수 없는 미래 API의 network 전 사전 거부
- configure-session POST 무재시도와 후속 step 중단
- 결과 불명확 request phase와 HTTP status 분류
- reflected SQL/secret의 Error, Observer와 lifecycle event 비노출
- metadata 검증 성공, 실패와 table/view 충돌
- background cleanup, `KeepSessionOnFailure`와 cleanup 오류 보존
- 같은 session 동시 setup 직렬화와 기존 `SessionRecipe` 회귀
- 기존 외부 `Client` 구현 compile 호환성
- `go test ./...` 통과
- `go vet ./...` 통과
- `go test -tags=integration ./...` compile 및 mock test 통과, 실제 Gateway test는 환경변수 부재로 skip
- `./build.ps1` 통과
- reachable symbol 및 전체 module graph `govulncheck`에서 알려진 취약점 없음

실제 SQL Gateway integration test는 `FLINK_SQL_GATEWAY_URL`이 설정되지 않아 skip되었다. 개발
환경의 `CGO_ENABLED=0` 때문에 `go test -race ./...`는 실행되지 않았으며 C compiler와 CGO가
준비된 환경에서 별도로 실행해야 한다.

## 알려진 제한

- table definition은 SQL parser로 해석하지 않으며 caller가 신뢰할 수 있는 SQL fragment를
  제공해야 한다.
- 영속 catalog 변경에 대한 자동 `DROP` rollback은 제공하지 않는다.
- metadata 검증은 객체 존재와 선택적인 DESCRIBE 성공을 확인하며 기존 객체가 요청 DDL과 완전히
  동일하다는 증명은 아니다.
- 실제 Gateway URL이 없는 개발 환경에서는 integration test가 skip된다.
