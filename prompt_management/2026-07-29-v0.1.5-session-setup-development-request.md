# flink-sql-go v0.1.5 Session Setup 기능 개발 요청

## 작업 목적

현재 `flinksqlgateway` 패키지는 다음 기능을 제공한다.

- `ConfigureSession`을 통한 Flink SQL Gateway `configure-session` 호출
- `SessionRecipe`를 통한 세션 생성 및 setup SQL 순차 실행
- `ListCatalogs`, `ListDatabases`, `ListTables`, `DescribeTable` 등의 metadata helper
- `QuoteIdentifier` 기반 식별자 quoting
- SQL 실행 POST 자동 재시도 금지 및 typed error 처리

이번 작업에서는 catalog, database, table과 현재 session scope를 선언형으로 구성할 수 있는 고수준 API를 추가한다. 기존 `SessionRecipe`는 범용 SQL replay 기능으로 유지하고, 신규 기능은 `ConfigureSession`을 중심으로 구현한다.

대상 릴리스 버전은 사용자 결정에 따라 `v0.1.5`로 한다. 공개 API 추가가 포함되더라도 임의로 `v0.2.0`으로 변경하지 않는다.

## Git 작업 기준

1. 원격 저장소는 `github.com/heartblast/flink-sql-go`다.
2. 작업 브랜치는 반드시 `0.1.5`를 사용한다.
3. `main` 브랜치에 직접 커밋하지 않는다.
4. 작업 시작 전 원격 `0.1.5` 브랜치를 fetch하고 해당 브랜치로 checkout한다.
5. 기존 사용자 변경사항이나 관련 없는 파일은 수정하지 않는다.
6. 기능 구현, 테스트, 문서와 버전 변경을 완료한 뒤 원격 `0.1.5` 브랜치에 push한다.
7. 권장 최종 커밋 메시지는 다음과 같다.

```text
feat: add declarative session setup for v0.1.5
```

## 핵심 설계 원칙

### 1. 기존 기능과 역할 분리

- `SessionRecipe`는 기존과 같이 `/statements`와 `ExecuteAndWait`를 이용하는 범용 replay 기능으로 유지한다.
- catalog, database, table과 `USE` 문을 구성하는 신규 기능은 `/configure-session`을 호출하는 `ConfigureSession`을 사용한다.
- 기존 공개 타입이나 메서드를 삭제하거나 이름을 변경하지 않는다.
- 기존 `Client` 인터페이스에 신규 메서드를 직접 추가하지 않는다. 외부 mock과 wrapper의 컴파일 호환성을 보존하기 위해 별도 인터페이스를 정의한다.

권장 인터페이스 예시는 다음과 같다.

```go
type SessionSetupExecutor interface {
    ApplySessionSetup(
        ctx context.Context,
        sessionHandle string,
        plan SessionSetupPlan,
        options SessionSetupOptions,
    ) (*SessionSetupResult, error)
}
```

### 2. 선언형 Setup 모델

다음과 같은 역할을 제공하는 공개 타입을 설계한다. 필드명과 세부 구조는 현재 코드 스타일과 테스트 가능성을 검토하여 조정할 수 있지만 역할은 유지한다.

```go
type SessionSetupPlan struct {
    Catalogs        []CatalogSetup
    Databases       []DatabaseSetup
    Tables          []TableSetup
    CurrentCatalog  string
    CurrentDatabase string
}

type CatalogSetup struct {
    Name          string
    IfNotExists   bool
    Options       map[string]string
    SensitiveKeys []string
}

type DatabaseSetup struct {
    Catalog     string
    Name        string
    IfNotExists bool
    Options     map[string]string
}

type TableSetup struct {
    Target    Identifier
    Statement string
    Verify    bool
    Sensitive bool
}
```

신규 공개 메서드는 최소 다음 역할을 제공한다.

```go
func CompileSessionSetup(plan SessionSetupPlan) ([]SessionSetupStep, error)

func (c *GatewayClient) ApplySessionSetup(
    ctx context.Context,
    sessionHandle string,
    plan SessionSetupPlan,
    options SessionSetupOptions,
) (*SessionSetupResult, error)

func (c *GatewayClient) OpenSessionWithSetup(
    ctx context.Context,
    request OpenSessionRequest,
    plan SessionSetupPlan,
    options SessionSetupOptions,
) (*SessionSetupResult, error)
```

`CompileSessionSetup`은 네트워크를 호출하지 않고 모든 입력을 먼저 검증하고, 실제 실행 순서가 확정된 step 목록을 반환해야 한다.

### 3. 실행 순서

가능한 한 완전 수식된 이름을 생성하여 session의 현재 catalog/database 상태에 대한 의존성을 줄인다.

기본 실행 순서는 다음과 같이 한다.

1. `CREATE CATALOG`
2. `CREATE DATABASE catalog.database`
3. `CREATE TABLE catalog.database.table`
4. `USE CATALOG`
5. `USE database`
6. 선택적 metadata 검증

단, raw `CREATE TABLE` 문이 객체명만 사용하여 현재 scope에 의존하는 경우에는 다음 중 하나를 선택하고 동작을 문서화한다.

- `TableSetup.Target`을 필수로 받아 라이브러리가 완전 수식된 DDL을 생성한다.
- scope 의존 raw SQL은 `USE` 이후 실행하도록 분류한다.
- 안전하게 판별할 수 없는 raw SQL은 compile 단계에서 거부한다.

단순 문자열 추측으로 SQL을 재작성하지 않는다. 이 프로젝트는 SQL parser를 포함하지 않는다는 기존 경계를 유지한다.

### 4. 식별자와 문자열 quoting

- catalog, database와 table 이름은 기존 `QuoteIdentifier`를 재사용한다.
- catalog option과 database option 값은 별도의 SQL 문자열 literal quoting 함수로 처리한다.
- 작은따옴표는 두 번 써서 escape한다.
- option map은 key를 정렬하여 항상 결정적인 SQL을 생성한다.
- 빈 식별자, 잘못된 target 조합, 중복 설정과 모순된 current scope는 네트워크 호출 전에 오류로 반환한다.

권장 helper 예시는 다음과 같다.

```go
func QuoteStringLiteral(value string) string {
    return "'" + strings.ReplaceAll(value, "'", "''") + "'"
}
```

공개 함수로 둘지는 API 최소화 원칙에 따라 결정한다.

### 5. `ConfigureSession` 결과 불명확 오류

현재 `ExecuteStatement`에는 `ErrExecutionOutcomeUnknown` 분류가 있으나 `ConfigureSession`은 POST 요청의 결과가 불명확한 경우 일반 transport/API 오류만 반환한다.

신규 setup 기능 구현 전에 `ConfigureSession`의 비멱등 POST 결과 불명확 상태를 typed error로 분류한다.

권장 형태는 다음과 같다.

```go
var ErrConfigurationOutcomeUnknown =
    errors.New("session configuration outcome is unknown")

type ConfigurationOutcomeUnknownError struct {
    SessionHandle string
    StepIndex     int
    StepKind      SessionSetupStepKind
    RequestPhase  RequestPhase
    Cause         error
}
```

구현 요구사항:

- `RequestNotSent`는 결과 불명확 오류로 분류하지 않는다.
- 요청이 전송됐을 가능성이 있고 응답이 유실됐거나 408, 429 또는 5xx 상태라면 보수적으로 결과 불명확으로 분류한다.
- `ConfigureSession`과 setup step은 자동 재시도하지 않는다.
- 결과 불명확 오류 발생 후 동일 DDL을 자동 재실행하지 않는다.
- 검증 대상이 명확한 경우 read-only metadata 조회로 상태 확인을 시도할 수 있으나, 확인할 수 없으면 `OutcomeUnknown`을 그대로 반환한다.
- 오류에는 SQL 원문을 포함하지 않는다.

### 6. 결과와 오류 모델

Operation이 없는 `ConfigureSession` 경로에 맞는 결과 타입을 추가한다. 기존 `StatementResult`를 억지로 재사용하지 않는다.

권장 결과 예시는 다음과 같다.

```go
type SessionSetupStepResult struct {
    Index          int
    Kind           SessionSetupStepKind
    Target         Identifier
    Applied        bool
    Verified       bool
    OutcomeUnknown bool
}

type SessionSetupResult struct {
    SessionHandle              string
    Steps                      []SessionSetupStepResult
    FailedIndex                int
    Complete                   bool
    SessionClosed              bool
    PersistentChangesMayRemain bool
}
```

실패 오류는 다음 정보를 보존하되 SQL과 option 원문을 저장하지 않는다.

- 원인 오류
- cleanup 오류
- session handle
- 실패 step index
- step kind
- 안전하게 노출 가능한 target
- 결과 불명확 여부

`errors.Is`와 `errors.As`가 원인 및 cleanup 오류를 탐색할 수 있도록 기존 오류 스타일을 따른다.

### 7. 비밀정보 보호

catalog option에는 비밀번호, access key와 token이 포함될 수 있다.

다음을 반드시 구현한다.

- 기본 민감 key 목록: `password`, `secret`, `token`, `access-key`, `secret-key`와 대소문자/구분자 변형
- `SensitiveKeys`로 호출자가 추가 key를 지정할 수 있게 한다.
- SQL 원문과 option map은 result, typed error, Observer와 lifecycle event에 포함하지 않는다.
- Gateway가 오류 응답에 SQL 또는 option 값을 반사한 경우 민감 값을 `********`로 치환한다.
- `fmt.Sprintf("%+v", result)`로도 민감 값이 노출되지 않도록 결과 타입에 원본 option을 보관하지 않는다.
- 빈 secret 값과 중복 secret 값도 안정적으로 처리한다.
- secret redaction 테스트에는 여러 민감 값, 작은따옴표 포함 값과 서버 반사 오류를 포함한다.

### 8. 검증 기능

`SessionSetupOptions`에 선택적 검증 기능을 둔다.

검증에는 기존 helper를 재사용한다.

- catalog: `ListCatalogs`
- database: `ListDatabases`
- table: `ListTables`
- table schema가 필요한 경우: `DescribeTable`

검증 요구사항:

- 생성 성공과 검증 성공을 구분해서 결과에 기록한다.
- 검증 실패가 DDL 미적용을 의미한다고 단정하지 않는다.
- 검증 API는 read-only 요청이므로 기존 안전 재시도 정책을 사용할 수 있다.
- 이름 비교의 대소문자 정책은 Flink 반환값을 존중하고 임의로 case-folding하지 않는다.
- 같은 이름의 table/view 충돌 가능성을 고려한다.

### 9. 실패 cleanup과 영속 변경

- `OpenSessionWithSetup`의 기본 정책은 setup 실패 시 생성한 session을 닫는 것으로 한다.
- 조사 목적의 `KeepSessionOnFailure` 옵션을 제공할 수 있다.
- session 종료를 rollback으로 표현하지 않는다.
- HiveCatalog 등 영속 catalog에 이미 반영된 객체는 session을 닫아도 남을 수 있다.
- 자동 `DROP` rollback은 구현하지 않는다.
- 일부 step이 성공한 뒤 실패했다면 `PersistentChangesMayRemain=true`를 반환한다.
- cleanup에는 취소된 caller context가 아닌 제한된 background context를 사용한다.

### 10. API 버전과 capability

- `ConfigureSession`은 v2 이상에서만 지원된다.
- `ApplySessionSetup`과 `OpenSessionWithSetup`은 v1에서 `ErrUnsupportedAPI`를 반환해야 한다.
- 기존 `Capabilities.ConfigureSession`을 재사용한다.
- 알 수 없는 미래 API 버전을 지원한다고 추측하지 않는 기존 보수적 정책을 유지한다.

## 필수 단위 테스트

`httptest.Server`를 사용하여 최소 다음을 검증한다.

1. catalog → database → table → `USE CATALOG` → `USE database` 순서
2. 모든 setup POST가 `/configure-session`으로 전송되는지 확인
3. v1에서 setup API가 네트워크 호출 없이 거부되는지 확인
4. option key 정렬과 결정적인 DDL 생성
5. 식별자 backtick과 문자열 작은따옴표 escape
6. 중간 실패 시 후속 step 미실행
7. 실패 index와 성공 step 목록 정확성
8. 기본 session cleanup과 `KeepSessionOnFailure`
9. setup POST 무재시도
10. 요청 미전송과 결과 불명확 오류 구분
11. 서버 반사 오류의 secret redaction
12. SQL 원문과 password가 Error, Observer, lifecycle event에 노출되지 않음
13. metadata 검증 성공 및 실패
14. 검증 실패 시 DDL 적용 여부를 단정하지 않음
15. persistent catalog 변경 잔존 가능성 표시
16. 기존 `SessionRecipe` 테스트와 동작에 회귀가 없음
17. 기존 외부 `Client` 구현이 신규 API 때문에 깨지지 않음
18. context 취소와 cleanup context 분리
19. empty plan, invalid identifier, conflicting scope 등의 compile-time 검증
20. `go test -race`에서 동시 호출 문제가 없음

## 통합 테스트

환경변수가 제공된 경우에만 실행하고, 없으면 skip하는 기존 정책을 유지한다.

가능하면 실제 Flink 1.20.4 SQL Gateway에서 다음을 검증한다.

1. temporary/in-memory catalog 또는 테스트용 catalog 생성
2. database 생성
3. table 등록
4. `USE CATALOG`, `USE database`
5. `SHOW CATALOGS`, `SHOW DATABASES`, `SHOW TABLES`, `DESCRIBE` 검증
6. session 종료 후 `default_catalog` 객체 수명 확인
7. 영속 catalog를 사용할 수 있는 환경에서는 session 종료 후 객체 잔존 확인

운영 catalog나 실제 데이터가 있는 table은 테스트에서 생성 또는 삭제하지 않는다.

## 완료 조건

다음 조건을 모두 만족해야 한다.

- 신규 setup API가 `ConfigureSession`을 사용한다.
- 기존 `SessionRecipe`의 의미와 동작이 유지된다.
- catalog, database, table과 current scope를 선언형으로 구성할 수 있다.
- 실행 전 compile/validation 단계가 존재한다.
- 부분 성공, 실패 위치와 결과 불명확 상태를 typed result/error로 확인할 수 있다.
- setup POST를 자동 재시도하지 않는다.
- 자동 rollback을 수행하지 않는다.
- SQL 원문, password, token과 secret이 오류와 관측 이벤트에 노출되지 않는다.
- 기존 `Client` 인터페이스 구현 호환성이 유지된다.
- metadata 기반 선택적 검증을 지원한다.
- 단위 테스트, vet와 가능한 검증 명령이 통과한다.
- 버전 관련 문서와 `VERSION`이 `0.1.5`로 정합화된다.
